# План переноса StreetRP с RAGE MP на FiveM

Дата: 06.10.2026. Статус: план, реализация миграции не начата.

## 1. Рекомендуемое решение

Пользователь выбрал максимально точное сохранение всех механик и обязательную замену MongoDB на MariaDB. Поэтому основной вариант — **FiveM + собственное ядро StreetRP + MariaDB + существующий Vue UI**, с заменой платформенного слоя RAGE MP и слоя хранения данных.

Пользователь согласовал MariaDB: ограничение по СУБД для Qbox снято. Теперь сравниваются **FiveM + StreetRP + MariaDB** и **FiveM + Qbox + адаптированные механики StreetRP + MariaDB**. Собственное ядро остаётся базовым вариантом при обязательном паритете; Qbox можно выбрать по результатам прототипа, если он реально сокращает поддержку без изменения механик. MariaDB соответствует текущим требованиям Qbox. [Требования Qbox](https://docs.qbox.re/installation).

«Как есть» означает сохранение игрового поведения, экономики, интерфейсов и данных. Сам код нельзя просто запустить в FiveM: потребуется заменить API, транспорт событий, синхронизацию, идентификацию и упаковку ресурсов.

Вариант **Qbox + StreetRP** имеет смысл, если стандартные системы Qbox удаётся использовать через публичные API с точным воспроизведением правил StreetRP и без постоянного изменения ядра Qbox. Если для сохранения механик приходится держать два инвентаря, две системы денег и две модели персонажа, упрощения не получится.

Решение о переносе действующих аккаунтов и имущества ещё не получено. План предусматривает обе ветки; очистка существующей базы не предполагается.

## 2. Что установлено по репозиторию

Это статический аудит исходников и выборочных модулей, без запуска игрового сервера и полной проверки функциональности.

| Область | Наблюдение | Следствие |
|---|---|---|
| Сервер | 241 TS-файл в `src_server/src`, в 165 есть `mp.*` | Много платформенных зависимостей внутри игровых модулей |
| Клиент | 99 TS-файлов в `src_client/src`, в 95 есть `mp.*` | Почти весь клиент потребует адаптации |
| UI | Vue 3, Vite, Pinia, обёртка `src_ui_vue/src/utils/rpc.ts` | Экраны и стили можно сохранять, заменить транспорт и интеграцию с игрой |
| UI-паритет | `CONVERTATION.md` заявляет 34 маршрута и 218 активных RPC-имён | Использовать как исходный список для проверки, повторно сверить актуальный код |
| Данные | Mongoose/MongoDB; отдельные User и Character | Qbox потребует отдельного проектирования модели и миграции |
| Деньги | Собственные MongoDB-операции и проверки остатка; донат на аккаунте | Нельзя одновременно вести баланс в MongoDB и Qbox |
| Инвентарь | Ячейки, вес, экипировка, быстрые слоты, предметы домов и машин | Замена на другой инвентарь затрагивает игровое поведение |
| Авторизация | Email/пароль, коды, `socialClub` и `serial` | Идентификаторы RAGE нельзя считать взаимозаменяемыми с FiveM |
| Персонаж | Обёртка PlayerEntity над PlayerMp, поля и helpers расширяют `mp` | Нужен новый контекст игрока и разграничение постоянных/сетевых ID |
| Мир | Dimensions используются для входа, персонажа и домов | Каждый сценарий изоляции нужно перенести отдельно |
| Бой | В клиенте отключается стандартный урон и определяется часть тела по выстрелу | Проверка точного поведения боя — ранний блокирующий эксперимент |
| Голос | Свои слушатели и вызовы RAGE voice | Новый голосовой backend с сохранением правил дистанции/телефона/ограничений |
| Контент | Работы, бизнесы, дома, полиция, армия, мафии, банды, награды, донат | Полный перенос существенно шире запуска персонажа и HUD |

Число файлов показывает распространённость API, а не процент кода, который необходимо переписать.

`database.sql` фактически содержит команды MongoDB, включая `drop()`. Это не SQL-миграция для Qbox; его нельзя запускать как импорт в новую базу.

## 3. Сравнение вариантов

| Критерий | FiveM + ядро StreetRP | Qbox + механики StreetRP |
|---|---|---|
| Сохранение поведения | Проще контролировать: остаются текущие правила | Требуется доказать совместимость моделей и правил |
| API RAGE / клиент / NUI | Переносить | Переносить в любом случае |
| Требуемая СУБД | MariaDB, полный переход с MongoDB | MariaDB, стандартная схема Qbox плюс таблицы уникальных систем StreetRP |
| Деньги, персонажи, предметы | Сохраняются существующие модели | Нужно выбрать владельца данных и переработать обращения |
| Готовые Qbox/QBCore-ресурсы | Требуют собственной интеграции | Доступнее, но не все совместимы и не все повторяют StreetRP |
| Первоначальная сложность | Платформенная адаптация и сетевые особенности | Та же адаптация плюс интеграция фреймворка и данных |
| Долгосрочная поддержка | Больше собственного кода | Меньше только при реальном использовании стандартных систем |
| Когда выбирать | Точный паритет — обязательное требование | Команда готова принять модели Qbox или адаптер доказывает полный паритет |

Совместимость Qbox с QBCore не означает совместимость с RAGE MP или `rage-rpc`. [Qbox FAQ](https://docs.qbox.re/faq).

## 4. Целевая архитектура для основного варианта

```text
Vue UI
  ↕ NUI: сообщения, callbacks, управление фокусом
FiveM client (TS → JS)
  ↕ ограниченные сетевые события / RPC
StreetRP server (TS → JS)
  ├─ игровые сервисы StreetRP
  ├─ repositories → MariaDB
  └─ платформенные адаптеры → FiveM / OneSync / голос
```

- Оставить TypeScript. FiveM поддерживает JS и серверные Node API; все используемые зависимости проверить на выбранном runtime. Переписывание всего проекта на Lua не требуется. [FiveM JavaScript](https://docs.fivem.net/docs/scripting-manual/runtimes/javascript/).
- MongoDB/Mongoose заменить repository-слоем поверх MariaDB-драйвера; версия сервера и драйвер фиксируются после проверки на FiveM Node runtime. Redis оценить отдельно по его фактическим задачам.
- На старте собрать один основной ресурс StreetRP с внутренними модулями, отдельно UI/stream-ассеты по необходимости. Не превращать каждый файл в отдельный ресурс.
- Ввести явные адаптеры событий, игроков, сущностей, мира и UI. Минимальная временная совместимость с текущими helpers допустима; полный эмулятор `mp.*` не планировать.
- Оставить пользовательские правила и операции с данными внутри серверных сервисов; клиент отвечает за ввод, визуализацию и локальные native-вызовы.
- Постоянный ID персонажа, ID сессии `source`, entity handle и network ID — разные типы. Не хранить `source` как владельца имущества.
- Объекты PlayerMp/VehicleMp не передавать по сети: передавать идентификаторы, разрешать сущность и проверять права на сервере.
- Реплицировать только разрешённое публичное состояние. Приватные данные, баланс и учётные записи не помещать в публичные state bags. Учесть ограничения вложенных обновлений. [State bags](https://docs.fivem.net/docs/scripting-manual/networking/state-bags/).
- Для RPC определить список доступных действий, форматы данных, таймауты, ошибки и отмену при отключении игрока. В `helpers/events.ts` есть ветки с никогда не завершающимся Promise — переносить такое поведение нельзя.

## 5. Как проверить вариант с Qbox

MariaDB согласована. Для эксперимента использовать отдельный стенд и тестовые данные. Qbox устанавливать по официальному recipe через txAdmin. Версии зависимостей зафиксировать. [Qbox installation](https://docs.qbox.re/installation).

Предлагаемое распределение ответственности, если эксперимент успешен:

| Данные/функция | Единственный владелец | Что остаётся у StreetRP |
|---|---|---|
| Сессия и базовые данные персонажа | qbx_core | Представление для UI, уникальные поля через согласованное хранилище |
| Наличные и банк | qbx_core | Правила начислений, покупок, налогов и журнал через адаптер |
| Инвентарь, если выбран ox_inventory | ox_inventory | Поведение предметов, UI при доказанной совместимости, бизнес-правила |
| Ранги jobs/gangs | qbx_core | Захваты, обязанности, планшет, уникальные права и фракционные сценарии |
| Донат, опыт, навыки, награды | StreetRP | Полная собственная логика |
| Дома, бизнесы, владение транспортом | Один выбранный сервис на каждый домен | Текущие правила; совместимость с другими ресурсами через API |

Это целевое предложение, а не утверждение о совместимости. В частности, пригодность существующего UI инвентаря для ox_inventory нужно доказать отдельно.

Вызовы Qbox делать через публичные exports; сложные объекты Lua преобразовывать в простые DTO, при необходимости через небольшой Lua-ресурс. Проверить TS↔Lua на прототипе. Не изменять внутренние таблицы Qbox из игровых модулей и не зеркалировать баланс обратно в MongoDB. [Qbox developer guide](https://docs.qbox.re/developers), [server exports](https://docs.qbox.re/resources/qbx_core/exports/server).

Первый прототип Qbox: персонаж → HUD → покупка предмета → экипировка → перенос в багажник → переподключение. Он должен сохранять ячейки, вес, быстрые слоты, остатки денег и права доступа StreetRP. Если это требует существенного форка Qbox/инвентаря либо постоянного двойного хранения, выбрать собственное ядро.

## 6. Этапы работ и критерии готовности

### Этап 0. Зафиксировать эталон и объём

1. Запустить исходный RAGE MP на тестовой копии базы и записать воспроизводимые сценарии.
2. Составить каталог механик по папкам server/client и маршрутам UI: вход, персонаж, HUD, инвентарь, оружие, транспорт, дома, бизнесы, работы, фракции, телефон, админка, награды, донат.
3. Для каждой механики записать входные условия, формулы, ограничения, ожидаемые события, результат и изменение базы.
4. Сверить актуальный список RPC и места прямого использования `mp` в UI, включая чат и bootstrap.
5. Зафиксировать требования к числу игроков, игровому build, допустимой задержке и целевому оборудованию. Эти значения пока неизвестны.
6. Определить необходимость переноса действующих данных и обязательность email-входа после миграции. Целевая СУБД уже выбрана: MariaDB.

Готово: есть перечень механик и критерии паритета; «сохранить всё» выражено проверяемыми сценариями.

### Этап 1. Устранить главные неизвестные и выбрать архитектуру

Создать минимальный стенд FiveM + MariaDB и отдельный стенд Qbox для сравнительного прототипа. Провести ограниченные эксперименты:

1. Vue HUD + меню инвентаря через NUI: запрос, ответ, серверное обновление, ESC, фокус, управление персонажем.
2. Два игрока + машина: сетевые ID, передача ownership, вход/выход, блокировка и восстановление после переподключения.
3. Бой: урон по частям тела, броня, попадание из/в машину, смерть, добивание и медицинские действия — сравнение с эталоном.
4. Qbox: сценарий из раздела 5 и таблица несовпадений.
5. MariaDB: транзакция покупки и передачи предмета, конкурентные запросы, rollback при ошибке и сохранение после reconnect.

Для каждого эксперимента записать затраченное время, необходимый объём адаптера, функциональные расхождения и обнаруженные ограничения.

Готово: выбран вариант и записаны основания. При обязательном паритете любое несовпадение должно иметь проверенное решение; иначе соответствующая замена не принимается. Рабочий запуск HUD сам по себе не доказывает простоту полного переноса.

Ориентир для этой проверки — 5–10 рабочих дней одного разработчика, знакомого с обеими платформами. Это предварительная оценка эксперимента, не обещание срока полного переноса.

### Этап 2. Сборка, транспорт и платформенные адаптеры

1. Добавить структуру FiveM, `fxmanifest.lua`, конфигурацию ресурсов, сборки server/client/UI и типы CitizenFX.
2. Заменить `rage-rpc`: NUI ↔ client ↔ server; сохранить имена и формы ответов там, где это позволяет оставить UI без переработки.
3. Каждый NUI callback обязательно завершается ответом; предусмотреть таймаут серверного ответа. [NUI callbacks](https://docs.fivem.net/docs/scripting-manual/nui-development/nui-callbacks/).
4. Перенести PlayerEntity и helpers: lifecycle игрока, телепорт, права, координаты, сущности, метки, точки взаимодействия, камеры, анимации, клавиши.
5. Реализовать и проверить очистку таймеров, обработчиков, фокуса и сущностей при остановке ресурса и отключении игрока.
6. Сервер получает отправителя из доверенного контекста события; проверяет аргументы, расстояние, владение, права и частоту вызовов.

Готово: вход на сервер, корректный цикл UI/RPC, два игрока, безопасное отклонение неверного запроса и очистка при остановке ресурса.

### Этап 3. MariaDB, игрок, учётные записи, интерфейс

До переноса игровых доменов подготовить SQL-схему и repository-слой:

- Базовые таблицы: accounts, characters, vehicles, houses, businesses, factions, faction_members, inventory_containers, inventory_items, account_tokens, bans, reports и money_ledger. Полный список вывести из всех 17 текущих моделей, не только из перечисленных примеров.
- Определить постоянные PK, связи и таблицу отображения старых Mongo ObjectId. Не смешивать ID аккаунта, персонажа и сетевой сессии.
- Связи владения, деньги, предметы и членство хранить в нормализованных таблицах. Внешность и гибкие настройки можно хранить в JSON после анализа запросов; весь Character одним JSON-документом не переносить.
- Зафиксировать типы денег и единицу расчёта; использовать точное представление, согласованное с игровыми формулами, без FLOAT/DOUBLE для балансов. Добавить ограничения и индексы по реальным запросам.
- Переписать `findOne`, `updateOne/$inc`, `populate`, middleware и сохранение моделей в явные repository-методы. Новый transport/API не должен зависеть от Mongoose Document.
- Для покупок, переводов и перемещения имущества использовать InnoDB-транзакции, условное списание/блокировку строк, журнал и защиту от повторного выполнения. Проверить недостаточный остаток, конкуренцию, откат и deadlock.
- Согласовать обновление кэша игрока с commit: сначала успешная запись, затем уведомление UI. Не подтверждать покупку до сохранения.
- Ввести версионируемые миграции схем и тестовые данные. Сверять SQL-результат с эталонными сценариями MongoDB.

1. Перенести регистрацию/вход/коды или привязку аккаунта к FiveM-идентификатору согласно выбранной политике.
2. Для существующих аккаунтов реализовать подтверждённую привязку: владение старым аккаунтом проверять паролем/кодом; `socialClub`/`serial` автоматически не сопоставлять.
3. Перенести создание и внешность персонажа, одежду, спавн, HUD, деньги, голод, опыт и лицензии.
4. Сохранить Vue-экраны; заменить CEF URL, транспорт, чат-интеграцию, фокус и RAGE bootstrap/mock.

Готово: персонаж создаётся/загружается, сохраняется и восстанавливается после reconnect; UI воспроизводит эталонные действия.

### Этап 4. Инвентарь, экипировка, оружие и медицина

1. Сохранить предметы, вес, ячейки, стаки, быстрые слоты, рюкзак, одежду, использование и передачу.
2. Перенести хранилища игрока, дома, фракции, машины и предметы на земле.
3. Перенести боевую модель с результатами эксперимента: боеприпасы, части тела, броня, смерть, анимации, лечение.
4. Проверить одновременные перемещения, повторные запросы, disconnect во время операции и запрет доступа к чужому хранилищу.

Готово: нет потерь/дублирования предметов; суммы денег и предметов после операции согласованы; боевое поведение совпадает с эталоном.

### Этап 5. Транспорт, дома, бизнесы и экономика

1. Транспорт: создание/удаление, ownership, ключи, топливо, здоровье, тюнинг, гаражи, багажник и сделки.
2. Дома: владение, вход, запирание, хранилище, продажи и спавн.
3. Бизнесы: покупки, налоги, доходы, склады и передача собственности.
4. Сохранить формулы цен, выплат, payday, ограничений и комиссий.
5. Проверить игровые ассеты и карты: форматы ресурсов, streaming, индексы одежды, props, модельные имена и game build.

Dimensions не заменять механически на buckets: FiveM рекомендует buckets для раздельных сессий, но отдельно предостерегает от использования их как общего решения для интерьеров. Для каждого типа дома выбрать и проверить способ изоляции. [OneSync](https://docs.fivem.net/docs/scripting-reference/onesync/).

Готово: покупки и сделки сохраняются после перезапуска; сущности корректно видны нескольким игрокам; права и изоляция домов работают по эталону.

### Этап 6. Остальные механики

1. Работы: стройка, почта, порт, контрабанда, угон, уровни и ограничения.
2. Фракции: полиция, армия, мафии, банды, захваты, розыск, арест, гаражи, форма и планшет.
3. Телефон, сообщения и звонки; голос с теми же правилами дистанции, mute, смерти и доступа.
4. Админка, репорты, баны, demorgan, наблюдение и журнал.
5. Ежедневные награды, промокоды, донат, рефералы, сервисы и API.
6. Пересмотреть античит с учётом FiveM; сохранить разрешённые игровые правила и заменить проверки, специфичные для RAGE.

Для голоса выбрать готовый backend только после проверки нужных возможностей; готовый ресурс не гарантирует совпадение текущего поведения.

Готово: весь каталог этапа 0 имеет пройденные сценарии или явно согласованное отклонение. При текущем приоритете отклонения без согласования не считаются завершённым переносом.

### Этап 7. Данные, проверка и запуск

Для выбранного варианта MongoDB → MariaDB: выгрузить данные из копии исходной базы, преобразовать BSON/ObjectId/даты и вложенные структуры, импортировать повторяемым скриптом с журналом, таблицей старых/новых ID и контролем дубликатов. Перенести ссылки владельцев и все связанные записи; проверить восстановление из backup и привязку аккаунтов. MongoDB после финального переключения не использовать как второе активное хранилище.

Если по результатам прототипа выбран Qbox: подготовить таблицу отображения `User._id → account ID`, `Character._id/uid → citizenid`, владельцев машин/домов/бизнесов, предметов, внешности, рангов, лицензий, доната и банов. Переносить данные повторяемым импортом с журналом и контролем дубликатов; runtime-операции делать через API. Контролируемый offline-импорт в схемы Qbox проектировать отдельно по зафиксированной версии.

Если выбран чистый старт: исходную базу сохранить; создать отдельную новую базу и тестовые данные. Решение о судьбе старых аккаунтов зафиксировать отдельно.

Общие проверки:

- Сверка количества записей, владельцев, остатков денег и предметов; отчёт по неизвестным предметам/моделям и потерянным ссылкам.
- Репетиция миграции на копии и измерение окна переноса.
- Тесты с несколькими клиентами: сделки, драки, машины, входы в дома, звонки и захваты.
- Прерывание операций, reconnect, рестарт ресурса/сервера; отказ базы и восстановление.
- Профилирование на целевой нагрузке; бюджет производительности определить на этапе 0.
- Для релиза остановить изменения данных RAGE, сделать final backup, выполнить перенос и smoke-сценарии. Подготовить возврат к исходной версии.
- После начала игры в новой системе откат требует решения по новым данным: простой возврат старой базы теряет прогресс. До запуска выбрать правило компенсации/переноса изменений.

Готово: воспроизводимый запуск, отчёт о паритете, проверенное сохранение данных и согласованный порядок отката.

## 7. Порядок принятия решения

1. Исходные требования уже известны: максимально точные механики и переход MongoDB → MariaDB.
2. Базовая архитектура для оценки — FiveM с собственным StreetRP и MariaDB.
3. Qbox оценить по конкретным заменам и пройденному прототипу; MariaDB уже согласована.
4. Считать экономию как «собственный код, который реально удаляется» минус «адаптеры, миграции, форки и сопровождение несовпадений».
5. Если Qbox не даёт положительной экономии при полном паритете, не включать его в основное ядро. Отдельные FiveM-ресурсы можно интегрировать независимо от выбора фреймворка, если их зависимости и API это допускают.

Полную оценку сроков составить после этапов 0–1: по каждому домену указать переносимые модули, сложность, интеграции, проверки и резерв. Сейчас неизвестны фактическое состояние всех механик, качество ассетов, объём живой базы и целевая нагрузка, поэтому точная дата полного переноса была бы необоснованной.
